# Choose the branding surface

Establish the instance release, active experience, requested surface and
effective access from available evidence. Catalog availability does not prove
the installed app version. If version metadata is denied, keep it unknown and
use accessible actual controls plus release-matched documentation.

| Target | Mechanism and reach |
|---|---|
| Next Experience and supported workspaces | Theme Builder for supported colors, typography, imagery, shapes and components. Verify each intended experience; custom components and app-shell overrides may differ. |
| Theme/palette choice | Distinguish published availability, default order and the named user's selection. An alternate light/dark palette is not created automatically. Fixed vendor themes are not ordinary editable custom drafts. |
| Login page | Documented login-specific settings and assets. Verify anonymous versus SSO scope separately; a login change is not a workspace theme. |
| Service Portal / Employee Center | Separate portal branding/theme configuration. Select the actual portal; Theme Builder publication does not prove portal branding. |
| Core UI without Next Experience | Use the release's basic/UI16 configuration, not the Next Experience theme workflow. |
| Mobile, external sign-in, email, PDFs, custom widgets | Include only when requested and independently supported. |

Use supported UI authoring or an administration tool implementing the exact
requested action. Table CRUD does not establish theme creation, upload,
publication or restoration semantics. A tool limited to one property or one
workspace icon is not a general branding API.

Rebranding changes presentation. Navigation, page layout and business content
need separate scope. Verify action-specific roles and asset controls without
granting access merely to make a branding task succeed.
